# Decision record: the loops design

This record holds the decisions the user confirmed for the loops design, with the reasons and what each one replaces. It was written by the run that set out to `Make dacapo loops data: files at three levels, a loop-driven runtime, a read-only viewer pane and an architect that edits drafts`. The run was held to the balanced level (QA as the end user, no engineering review) and leaves dacapo at version 0.22.0. Decisions are cited by id, `D1` to `D14`.

## Decisions

### D1 Loops are plain files at three levels

A loop is a folder of plain files at one of three levels.

- Plugin: shipped, read-only, at `<plugin root>/loops/<name>/`.
- User: at `$DACAPO_HOME/loops/<name>/`, where `DACAPO_HOME` defaults to `~/.claude/dacapo`.
- Project: at `<repo>/.claude/dacapo/loops/<name>/`, kept out of git through `.git/info/exclude` like `.workspaces/`.

A name resolves project over user over plugin.

Why: loops must be data a person can design (see Context, why data).

Supersedes: nothing.

### D2 No levels inside a loop

A loop has no levels. Depth is a separate loop. The plugin ships three: `core` (QA, no review; the default), `core-fast` (no judges) and `core-deep` (QA, then review in the next step). The `level` and `judges` conf keys and the `--fast`, `--balanced` and `--deep` flags go. `--loop <name>` and a `loop` conf key come.

Why: see Context, why no levels.

Supersedes: the fast, balanced and deep levels, and the `level` and `judges` conf keys.

### D3 Orchestrator-only steps stay explicit as stages

The steps only the orchestrator performs (clarify, research, plan, merge) stay explicit as stages with no nodes, so the run pane tracks them.

Why: the run pane tracks stages, and a step with no agent would otherwise leave no mark.

Supersedes: nothing.

### D4 A node may live outside any stage

A node may live outside any stage. It is on call: usable at any point, with optional helper nodes of its own. Deleting a stage never deletes its nodes. They go on call.

Why: see Context, why on call sits inside the orchestrator's tile.

Supersedes: nothing.

### D5 The loop pane is a read-only viewer

The loop pane is a read-only viewer. It offers navigation, focus, fold, Save and Discard. Every edit, including creating, renaming, moving and deleting loops, goes through the architect's tools with fixed operations. `/dacapo:design` is the one entry and opens the library.

Why: see Context, why a read-only viewer.

Supersedes: nothing.

### D6 Canvas text is sparse

Canvas text is a name plus a summary of two to four words for each node and stage. A forward transition carries a condition of two words. A back transition, a handover stub and an agent-to-agent edge carry one word. Everything else lives in the focus panel.

Why: see Context, why sparse text with a summary.

Supersedes: nothing.

### D7 Two edge kinds

There are two kinds of edge.

- Transitions join stages, or an entry or exit, and always belong to the orchestrator. They are dashed, forward down the left and back up the right, each with a condition.
- Handovers join two nodes and carry a spec. A handover with the orchestrator is drawn as a stub on the agent. A hollow circle stands for the orchestrator.

Why: see Context, why stubs for handovers with the orchestrator.

Supersedes: nothing.

### D8 Entry and exit tiles share one shape

The entry and exit tiles share one shape. The exit node is named `done`.

Why: one shape makes the two ends of a loop read as a pair.

Supersedes: nothing.

### D9 File formats

A node is one markdown file: YAML-shaped frontmatter plus the role as the body. The graph is `loop.json`. The diagram is `loop.d2`, in a D2 subset the plugin writes and parses itself, with no d2 binary. Each loop also has a generated `LOOP.md`, a prose spec.

Why: see Context, why JSON for the graph, markdown for nodes and a D2 subset for the diagram.

Supersedes: nothing.

### D10 The runtime reads the active loop

The runtime reads agents, models, skills, tool denials, stages and summaries from the active loop. A node declares one of four contracts that the host implements: `lands`, `scores`, `collects` or `none`. Worktrees, pull requests, report validation, verdicts, wake-ups and guards are unchanged.

Why: see Context, why data.

Supersedes: the seven hard-wired phases in the pane; the four hard-wired agents and prompts in `hooks/register.tsx` and `hooks/prompts.ts` (the shipped `core` loop carries them as files instead); the `qa` and `review` tools (one `judge` tool takes the node) and the `phase` tool (a `stage` tool).

### D11 Every loop stays accessible as plain files

Every loop at every level stays accessible outside the plugin as plain files. Nothing about a loop lives only in the plugin's store. The store holds view state only.

Why: a loop that only the plugin can read is not data a person owns.

Supersedes: nothing.

### D12 `DACAPO_HOME` overrides the user-level root

`DACAPO_HOME` overrides the user-level root, for loops and drafts. Tests and QA never touch the real folder.

Why: tests and QA must not change what the user has on disk.

Supersedes: nothing.

### D13 End-to-end runs use a scratch repository

End-to-end test runs use the scratch repository `nunomota/dacapo-scratch`.

Why: a real run opens pull requests and merges them, so it needs a repository that can take that.

Supersedes: nothing.

### D14 The loop skill stays hand-written

The loop skill `skills/loop/SKILL.md` stays hand-written, host-agnostic prose. The shipped `core` entry node preloads it through `skills: [dacapo:loop]` instead of duplicating it.

Why: one copy of the spec cannot drift from itself, and it stays independent of any host.

Supersedes: nothing.

## Context

Some reasons span several decisions.

**Why data.** The loop spec and the core binding were split by text only. The mod still hardcoded four agents, their prompts, the tool set and the phase list, so a loop that added a node or a stage could not run. Making loops data lets a person design other loops without touching orchestration. This drives D1 and D10.

**Why no levels.** With arbitrary loops, a level is just a smaller or larger loop. Three shipped loops are simpler than a level concept inside every loop. This drives D2.

**Why a read-only viewer.** One editing path gives one validation path. The pane renders the same on every surface: the plugin API offers Box, Text, Button, Input, Select, Link and an SVG string on desktop, with no HTML and no clickable SVG. The architect's operations become the public API of a loop. This drives D5.

**Why JSON for the graph, markdown for nodes and a D2 subset for the diagram.** The plugin has no dependencies and no YAML parser. Node files match the shape of Claude Code agent files. D2 renders in other tools and is readable, but a binary must not be required. This drives D9.

**Why on call sits inside the orchestrator's tile.** Agents without a stage belong to the orchestrator and must not look like a step. Folding keeps the tile small. This drives D4.

**Why stubs for handovers with the orchestrator.** A line from the orchestrator to every agent made the canvas unreadable. A line from QA to the workers read as QA dispatching work. Transitions are the orchestrator's by definition, so they are drawn stage to stage. This drives D7.

**Why sparse text with a summary.** Names alone were too bare and full metadata was too noisy. A few words of purpose per entity is the middle. This drives D6.

## Superseded

The design replaces these:

- The fast, balanced and deep levels, and the `level` and `judges` conf keys (D2).
- The seven hard-wired phases in the pane (D10).
- The four hard-wired agents and prompts in `hooks/register.tsx` and `hooks/prompts.ts`. The shipped `core` loop carries them as files instead (D10).
- The `qa` and `review` tools, replaced by one `judge` tool that takes the node, and the `phase` tool, replaced by a `stage` tool (D10).
