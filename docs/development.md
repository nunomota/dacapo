# Developing dacapo

```
claude plugin validate .
claude plugin test .
node scripts/mirror-loops.mjs
```

The third command rebuilds `loops/shipped.ts` from the shipped loop folders; run it whenever a file under `loops/<name>/` changes, and commit the result with the change.

Mods are built on function hooks (`hooks/register.tsx`), an early-access Claude Code API; it may change between releases. Pull request state comes from one `gh pr list` call every 20 seconds on the mod's timer. Cost estimates use Anthropic list prices per model; override them with the plugin's `prices` option (`claude plugin configure dacapo`).

To try a development build, start Claude Code on this folder: `claude --plugin-dir <path to this repository>`. Set `DACAPO_HOME` to a temporary folder to keep your own loops, drafts and user conf out of it.

## Layout

| Path | What it holds |
| --- | --- |
| `skills/loop/SKILL.md` | The loop's specification: roles, variants, boundaries, host guarantees, report contracts, decision rules. Host-agnostic. |
| `skills/core/SKILL.md` | How this plugin runs a loop: its tools, subagents, worktrees, pull requests and wake-ups. |
| `skills/design` | The architect: how `/dacapo:design` reads what the user says into operations on a loop draft. |
| `skills/rules-commits`, `skills/rules-prs` | The commit and pull request rules workers follow by default; `commits-skill` and `prs-skill` in the configuration can name others. |
| `loops/` | The shipped loops, `core-fast`, `core` and `core-deep`, one folder each: `loop.json`, `nodes/*.md`, `loop.d2`, `LOOP.md`. |
| `loops/shipped.ts` | The shipped loop files as text, for the tests, which get no file system. Generated by `scripts/mirror-loops.mjs`. |
| `hooks/register.tsx` | The mod: tools, agents, guards, the ticker, the run's state. |
| `hooks/pane.tsx` | The pane and the band above the prompt. |
| `hooks/loops.ts` | The loop model: the three roots, reading and writing a loop folder, node frontmatter, validation, `LOOP.md`, listing, drafts. |
| `hooks/loopd2.ts` | Writing and reading `loop.d2` in the D2 subset. |
| `hooks/looplayout.ts` | The loop canvas: its layout, and its rendering as SVG or terminal lines. |
| `hooks/viewer.tsx` | The loop viewer pane: the library, the canvas and the focus panel. |
| `hooks/architect.ts` | The architect's operations on a draft and the loop folder operations: new, rename, move, delete, default, save. |
| `hooks/prompts.ts` | What the mod appends to a node's role for its contract, and the brief builders. |
| `hooks/conf.ts` | Reading and merging `dacapo.conf` files. |
| `hooks/report.ts` | Rubric and report validation, verdicts. |
| `dacapo.conf` | The shipped defaults; the keys users copy and edit. |
| `types/index.d.ts`, `types/loops.d.ts` | The run's state types; the loop, draft and viewer types. |
| `tests/dacapo.test.ts` | The mod's test suite, run with `claude plugin test .`. |
| `tests/loops.test.ts`, `tests/loopd2.test.ts`, `tests/looplayout.test.ts`, `tests/viewer.test.ts`, `tests/architect.test.ts` | The tests of the loop model, the D2 subset, the canvas, the viewer and the architect. |
| `scripts/mirror-loops.mjs` | Rebuilds `loops/shipped.ts`. Plain Node, no dependencies. |
| `docs/decisions/` | Decision records: what a run decided, why, and what it replaced. |

## Known limits

- The QA agent and its collectors keep a shell so they can run the deliverable, so reading source through a shell command is forbidden by their prompts rather than by the tooling.
- Collectors run in the foreground of QA's turn: the Agent hook forces `run_in_background: false`, since a QA turn that ended to wait on a background collector would be the round ending, collected without a report. Several Agent calls in one message still run at once, so a batch costs its slowest collector, and QA cannot walk its own items while one runs.
- Branch protection that requires reviews stops a worker's merge and the final merge; the orchestrator is told, and merging on GitHub by hand finishes the run.
- The timeline lives for the session; it is not kept across restarts.
- The configuration is read when a session starts, when a `/dacapo:core` prompt opens a run and when `/dacapo-config` runs; a file edited mid-run applies to the next run.
- The agents of every loop at the three levels register when a session starts. A loop saved or changed mid-session runs in the next session, like the configuration, and `start` says so when its agents are missing. A session holds one role per agent type, so two loops whose nodes share an id with different roles cannot both run in one session: the loop that wins resolution for that name registers its version, and `start --loop` on the other refuses and asks for a new session with `loop = <name>` in the conf.
- `loops/shipped.ts` is a copy. A shipped loop changed without running `node scripts/mirror-loops.mjs` leaves the tests reading the old files.
- `loop.d2` is read as the subset dacapo writes: shapes with a class and a summary as their `tooltip` (an older file's `summary` attribute still reads), one container per step labelled `step N`, transitions and handovers. Anything else at the top level is kept verbatim and written back; anything else inside the generated part is a problem the import names by line.
- The handover to an interviewing node was verified in the terminal. In the desktop app the view switch is unverified; `/dacapo-back` and the band's Back button return the view. A mod cannot start teammates, so the node runs as a background agent the mod routes the user's words to.
- Print mode cannot finish a run. `claude -p` ends when the turn ends, and nothing keeps the process alive after `finish` for the mod's timer to merge the final pull request and wake the orchestrator. Try a development build interactively with `claude --plugin-dir`.
